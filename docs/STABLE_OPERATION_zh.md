# 稳定运行与版本交付（当前工程预览）

> 当前总 Gate：**FAIL**。本文是保全、交接和后续验证的操作顺序，不把已经报告的运行、合成检查、构建或配置保存写成稳定交付。

## 先处理正在运行的另一台 Windows

用户报告另一台 Windows 正在运行约 30 分钟，且已确认画面为**合成**来源；已经收到两处独立副本修复的口头说明；具体执行模式、事件负载、补丁内容、源码版本、配置及最终日志仍**待核验**，所以该报告尚未验证，也不能计为通过，更不是 Seetong 或真实现场验证。不要为了套用本文而中断它；保留原安装目录与独立修复副本，实际路径填写在本机记录中。

运行自然停止后，在原机、原目录保留以下只读副本到一个带 `RUN_ID` 的新结果目录。先复制再查看，原始文件不改名、不清理：

1. 记录开始/结束时间、操作者、运行模式（`demo`、`replay` 或真实窗口）、实际来源、十路是否同时启用、模型是否启用，以及任何手工停止或强制结束。
2. 保存控制台标准输出/错误、应用日志、生成报告、进程退出码、`events.sqlite3` 及同目录 `events.sqlite3-wal`、`events.sqlite3-shm`、配置文件、证据清单、媒体和预览的路径。数据库仍被写入时，不把单独复制的主库当作一致备份；先按“更新”一节完成停止和排空，或使用已验证的一致性备份方式。
3. 记录源码身份：`git rev-parse HEAD`、`git status --porcelain`、补丁文件/未提交文件清单和每个实际使用配置、报告、脚本的 SHA-256。若不是 Git 工作副本，记录来源 ZIP 的 SHA-256 和解压目录。
4. 记录环境身份：精确 Python 版本、`pip freeze`、实际 Python/导入路径、OpenCV、采集提供方、Ollama 可执行文件和模型 digest、CPU/GPU/驱动、磁盘与文件系统。`pyproject.toml` 的宽版本范围不是固定环境。
5. 复制原始资源时保留文件时间戳和相对目录；不得上传现场画面、配置或凭据到公开仓库。

在任何“更新”前，比较这份副本与计划下载的源码：提交/ZIP 哈希、未提交差异、依赖、配置 schema、运行脚本和输出位置。Windows 上若已有修复，先把差异审阅、测试并回收为候选改动；不能用下载的新目录静默覆盖它。`f9018b24cecdcd39a69d45886f1addaaf6279a5a` 是本轮交接前已核对的文档/诊断基线，**没有**修复运行时失败。

新的用户报告称：Windows 执行者曾在**隔离修复副本**的两个运行时位置修改慢录像和停止进程挂起，原安装目录未改；本次长测和关停仅生成测试工具、日志和报告，未再改业务代码。先接收两处补丁、所用测试工具及 30 分钟日志/媒体/退出记录，审计补丁和完整媒体、退出证据，再与原目录和基线对账，才可形成待审阅的合并候选。不要因为这份报告自动重跑 P0/P1；仅在收到材料有证据缺口时，按缺项补做。

## 交付物、下载和本地运行边界

Seetong 仍是原有监控客户端。Factory Monitor 是另一套在本机运行的桌面工程：GUI、其采集/检测/录像/复核子进程，以及可选的仅本机回环模型服务。GitHub 只分发源码、版本和文档，不托管实时监控；当前现场链路不需要 Docker、远程代理或云端服务。

当前正式可获取的发布标记是预发布 `v0.1.0-preview.1`（提交 `4abaa0ba60ff61af4418a1f27be0d0941a67263b`），没有上传的 wheel、EXE 或其他发布资产。构建脚本目前只在 Windows 的项目环境生成 wheel 和 sdist，**不会生成 EXE**。因此本阶段的可复现交付是固定源码 ZIP/Git 加每台机器独立的项目内 `.venv`、模型和工具；不是“下载即用”的成品。

在未运行过项目的新目录进行下载和准备；不要克隆/解压到运行中目录或任何有未核对改动的目录。下面固定的是已审计的诊断基线，便于复查失败，**不是修复版**；下载 ZIP 时用 [该固定提交的源码 ZIP](https://github.com/wailliamkf-commits/factory-monitor/archive/f9018b24cecdcd39a69d45886f1addaaf6279a5a.zip)，并将下载文件 SHA-256 和对应提交填入同一次运行记录。

```powershell
$SourceCommit = 'f9018b24cecdcd39a69d45886f1addaaf6279a5a'
$TargetDir = 'D:\factory-monitor\factory-monitor-f9018b24'
if (Test-Path -LiteralPath $TargetDir) { throw 'Target already exists; choose a new empty directory. Do not overwrite it.' }
git clone https://github.com/wailliamkf-commits/factory-monitor.git $TargetDir
if ($LASTEXITCODE -ne 0) { throw 'Clone failed; stop and retain the error.' }
Set-Location -LiteralPath $TargetDir -ErrorAction Stop
git checkout --detach $SourceCommit
if ($LASTEXITCODE -ne 0) { throw 'Exact source checkout failed; stop and retain the error.' }
if ((git rev-parse HEAD).Trim() -ne $SourceCommit) { throw 'Source identity mismatch; stop.' }
powershell -ExecutionPolicy Bypass -File .\scripts\setup-windows.ps1
if ($LASTEXITCODE -ne 0) { throw 'Environment setup failed; stop and retain the error.' }
```

这会在该目录创建 `.venv`，而不会复制旧电脑环境、配置、数据库、录像或模型。随后按 [Windows 交接](WINDOWS_HANDOFF_zh.md) 手动取得并校验获准的模型和本地 Ollama 工具；许可证、打包权和干净 Windows 重现尚未验证，模型不能随源码混装分发。

先固定配置和数据目录，再运行只读预检；确认 JSON 的实际内容而非只看退出码。启动器默认打开合成 demo，真实窗口必须由现场操作员在 GUI 内选择并明确开始。

```powershell
.\.venv\Scripts\python.exe -m factory_monitor init --config config.json
.\.venv\Scripts\python.exe -m factory_monitor preflight --config config.json --data-dir data
.\scripts\launch-factory-monitor.ps1
```

真实窗口、布局、每路编号、裁剪、ROI、排班和心跳必须保存、关闭、重开并核对。自动放大/返回/原生点击未交付，仍只能由操作员在 Seetong 中手动切换。云端图像复核保持关闭。合成采集/录像测试可以关闭本地模型复核；一旦主张真实推理 Gate，就必须使用并记录指定模型身份，不能省略模型或用合成结果替代 15 秒复核证据。

## 可靠性测试如何排程

旧 Windows 十路合成复测并未通过：十段媒体各 101 帧、50.5 秒、35 个缺口，采集进程报告停止后仍被强制结束（`-15`）。`81` 是语义有歧义的累计队列计数，既不是精确丢帧数，也不是严格下限。详见 [复测审计](WINDOWS_RETEST_AUDIT_2026-09-22_zh.md)。因此不要先拉长时长、降低要求或以“运行过 30 分钟”替代修复。

| 阶段 | 必须先具备的证据 | 本阶段要回答的问题 | 状态 |
| --- | --- | --- | --- |
| P0 | 固定源码/环境/配置/来源身份 | 对照能否复现、差异是什么 | 待回收核验 |
| P1 | Windows 子进程内的阶段计时、队列账目、退出栈 | 证据热路径和停止阻塞在哪里 | 待回收核验 |
| P2 | P1 的单一主因 | 仅修该主因，并保留容量、恢复与缺口语义 | 待回收核验 |
| P3 | 定向回归和完整报告 | 两次相同的 94 秒十路、10 个同时事件突发均通过 | 按缺项补齐 |
| 工作负载 | 经审阅的 P3 修复和独立新输出目录 | 30 分钟合格工作负载、2 小时增长/压力、完整班次、误报暴露、72 小时 | 按缺项补齐 |

现有 `scripts/qa_ten_camera_smoke.py` 的 `--seconds` 仅允许 94–105 秒，适合保留原短夹具参数。它是合成容量检查，遇到运行错误会在完整媒体审计前退出；即使使用它，每轮仍须补做所有十段的逐帧完整解码、实际时间戳、缺口、预览、数据库、退出码与最终队列账目的事后审计。不要调用它的 `--seconds 1800`，也不要把它当成长测工具。

P3 不能只依赖当前脚本：修复后可使用已审阅、与原业务参数兼容且能在异常后继续完整媒体审计的验证工具。当前脚本的 CLI 限制仅说明它不能运行 `--seconds 1800`；它不禁止通用运行入口持续运行，也不能证明十路持续负载验收。当前缺少的是**已验证的十路持续负载验收工具**。

30 分钟、2 小时、完整班次和 72 小时需要修复后由已审阅的工作器/编排方式执行并记录。本仓库尚未交付经过验证的持续负载夹具；Windows 新增测试工具须先回收审阅，可复用已经有证据的部分，缺失部分才补实现。合格的补充负载至少应产生 3 个互不重叠的十路同时突发（至少 30 个完成事件），首个突发在缓存预热 30 秒后，每个后续突发等待前一批的 60 秒后录制、封装与解码核验完成，并满足实际规则冷却条件后，且每次使用允许的夹具产生的不同事件 ID。配置保留上限维持 20，不能把上限调大；测试产生超过 20 个事件以施加保留压力。任何即将淘汰的证据先完成逐帧解码并写入保留账本，删除前比较账本，确保 20 条上限不会让 30 条事件的完整性无从追溯。此工作负载与正在运行的半小时合成测试无关，后者仍按开头保全。仅延长无事件时长不能证明证据容量；真实无事件观察可以记录可观测性和稳定性，却不能证明同时事件、保留或在途压力能力。

不得放宽原门槛：单路缺席 5 分钟；候选延迟 p95 不超过 3 秒；从标注的最早可识别物料帧或缺席条件满足时刻起算的首次模型复核延迟（含队列）p95 不超过 15 秒。94 秒源媒体及每段至少 88 秒连续证据只适用于原 94 秒短夹具，不可错误套用于所有长测媒体。每一级失败就保留证据并回到前一诊断点；未执行不等于通过。

## 每次运行必须可回答的遥测问题

把 [持续运行记录模板](../scripts/acceptance/stability-run.template.json) 与同一次 [会话记录模板](../scripts/acceptance/session-record.template.json) 一起填写。空值写 `UNKNOWN` 或 `null`，不要用 `0` 伪装容量已测。

- **十路覆盖：** 每路写实际可观测秒数和计划应可观测秒数；缺口区间可以保留多个原因标签（unavailable、mapping invalid、frozen、blind、停止等），但统计时按时间并集去重，主原因/去重规则不得掩去其他原因。重置/缺席不应被默默归为正常。
- **事件与损失：** 写明预期/观测候选、同时突发暴露、队列 `attempted_new`、`accepted_new`、`rejected_new`、`evicted_old`、`consumed`、`remaining`、`shutdown_discarded`，以及测量方法。无法取得最终账目即为未知。
- **延迟：** 候选和复核延迟含队列等待；分母包含 timeout、未知、丢失和错误，不能只报完成样本。另存原始样本和时钟对齐方法。
- **证据：** 每个媒体完整解码到末帧，保存实际帧时间戳、播放时长、间隙与读回结果。`recording_status=complete` 仅代表封装结束；有缺口或未知时不可称“完整证据”。
- **资源与退出：** 保存 CPU、RAM、磁盘趋势的原始路径、进程树、日志、停止请求、排空、各 worker 返回、退出码、残留进程和最终队列计数。采样峰值不能代替全程趋势。

当前没有“永久无人值守”看门狗。期望运行态包括 `running`、可观测/不可观测、冻结、映射失效、停止中、已停止和失败；统一健康汇总、受限自动重启及恢复结果核验的完整流程尚未交付；现有状态消息不等于这些功能已完成。在此之前只允许现有的人工观察、人工停止和本地日志保全；不要把计划中的自动恢复当作已交付功能。

## 更新、停止、回退

更新必须安排在已知维护窗口。其正确顺序是：

1. 停止接收新工作；记录停止请求时间与理由。
2. 让已在途的采集、证据、复核和数据库写入排空；记录每个 worker 的自然退出和最终队列账目。若被迫终止，标记不一致/未知，不能宣布干净停止。
3. 以一致方式备份旧版本的源码身份、配置、数据库加 WAL/SHM、证据和原始日志；拒绝同时写入者。一个数据库只能由一个运行实例写入。
4. 将新版本下载/克隆到**新的**版本目录；新建其 `.venv`、工具、模型和输出根目录。绝不覆盖运行目录、脏工作树或旧数据目录。
5. 比较配置 schema、数据目录约定、导入版本、模型和采集提供方；先预检和小范围已审阅验证，再安排本节的测试阶梯。
6. 更新失败时，仅启动保留的上一版本和它相容的数据库/证据副本。不要用旧数据库覆盖新版本已产生的数据；先隔离、导出并审阅新数据后再决定迁移。

未来的便携发布应优先是每用户目录可解压、可回退的 Windows 便携包，再评估安装器；它必须先在干净 Windows 完成安装、捕获、证据、更新/回退和卸载验证，并固定依赖约束/锁定、检查第三方依赖和模型许可证、分离模型下载。该计划目前未实现，不能提前承诺 EXE、自动更新或守护服务。
