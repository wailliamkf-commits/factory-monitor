# 单屏主动巡视与 Computer Use 研究

核查日期：2026-09-25。仅使用公开的一手资料；没有下载模型权重、访问设备或处理生产监控画面。下文以【已核实】标记公开资料直接支持的事实，以【推断】标记由这些事实得到的架构判断，以【现场验证】标记公开资料不能替目标客户端作答的问题。

## 架构结论

**将 Computer Use 用于一次性标定、界面变化后的诊断和人工批准的校准更新；实际巡视使用可复现的确定性状态机。**不要让在线视觉大模型在每次巡屏时自由决定点击位置和下一步。Windows UI Automation 能读写客户端实际暴露的控件；截图 OCR 可核对画面标签、菜单文字和状态。只有在这两者都无法稳定定位的区域，才以经人工标定的屏幕坐标作为有限回退，并在每次动作后检查状态、失败即停止并提示人工处理。【推断】

单屏本身仍是感知瓶颈。9/16 宫格可能让单路人物或动作只占少量像素；把某一路切到大画面能增加显示像素，但若只是放大现有解码画面，就不会生成源画面里不存在的细节。【推断】若操作员为细节逐路放大，其他未放大的路在这段时间内没有被单屏采集链路观察。【推断】若每路停留 `d` 秒、切换另需时间 `s`，十路串行一轮的最短回访间隔约为 `10 × (d + s)`；某路在两次访问之间完全发生、结束的短事件可被漏过。缩短间隔只能缩短盲区，不能消除它。【推断】

## 模型与运行时成本

- **UI-TARS：能力与发布体积都不支持把公开 7B 检查点直接当作 16 GB 显存本地运行方案。** ByteDance 官方仓库在 2025-09-04 宣布 UI-TARS-2，并提供桌面点击、键盘等动作格式；本次没找到官方 UI-TARS-2 本地检查点的发布证据。对本次可核到的 UI-TARS-1.5，旗舰版本与 7B 公开版在 OSWorld 上分别报告 42.5 与 27.5，ScreenSpot-Pro 分别为 61.6 与 49.6。旗舰版本标为 early research access；官方同时列出 GUI 误识别、推理资源要求较高等限制。[官方 UI-TARS 仓库](https://github.com/bytedance/UI-TARS)；[公开模型卡](https://huggingface.co/ByteDance-Seed/UI-TARS-1.5-7B)
- **权重占用不能从“7B”标签直接推导。** 截至核查日，公开的 UI-TARS-1.5-7B 模型仓库显示总文件体积约 33.2 GB、许可为 Apache-2.0。该数字是检查点下载/磁盘大小，不等同于显存需求；但权重文件总量已经超过 16 GB 显存，因此原样装入 16 GB 显卡不可行，量化、CPU 卸载、运行时和上下文空间都会改变实际资源与速度，必须另测。【已核实】
- **Qwen3-VL 有直接相关的 GUI 能力，也存在同样的本地资源边界。** Qwen 官方仓库列有计算机使用、屏幕定位与动作规划 cookbook，并明确建议中国大陆用户优先使用 ModelScope 获取检查点；这是上游建议，不证明特定镜像、版本或网络当日可达。[Qwen3-VL 官方仓库](https://github.com/QwenLM/Qwen3-VL) Hugging Face 上的官方 Qwen3-VL-8B-Instruct 卡片报告约 9B 参数、BF16，文件树合计约 17.5 GB。此未量化权重已大于 16 GB 显存，尚未包含图像输入、KV cache 和推理工作区；因此 16 GB 显卡若要运行，需评估量化或卸载，不能从模型卡承诺可实时操作。[官方模型卡与文件列表](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct/tree/main)
- **PaddleOCR/ONNX 更适合作为轻量界面读数层，不是监控动作理解模型。** PaddleOCR 文档提供 PP-OCRv5 mobile 检测模型 4.7 MB、中文识别模型 16 MB；它们的职责是定位和识别文字，可读相机标题、菜单和状态字样，不能据此识别画面中人的动作。[模型列表](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/model_list.md) PaddleOCR 3.5 支持 Paddle、Transformers、ONNX Runtime 等推理引擎，且建议一个环境只装一种引擎以免依赖冲突；ONNX Runtime 可配置 CPU/CUDA provider。其公布的速度依赖各自测试硬件，不能当作当前电脑的延迟保证。[推理引擎文档](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/inference_deployment/local_inference/inference_engine.en.md) [OCR 管线及其自测指标](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/OCR.md)

**选型对当前架构的影响：**先用 UIA 探查、人工确认和 OCR 把固定监控客户端的窗口、宫格、选中路、单路大画面、返回宫格等动作校准为带断言的有限状态机。模型只处理未知/变化界面的定位建议，不持有无人监督的点击权限。小型 OCR 模型可常驻 CPU；GUI VLM 作为可选诊断组件按需调用，不与主检测 GPU 抢资源。此为架构建议，模型未安装，也未在目标硬件计时。【推断】

## Windows UI Automation 的边界

【已核实】Windows UI Automation (UIA) 提供桌面控件树、属性、控件模式和事件，标准 Win32、WinForms、WPF 等控件有系统提供的 provider。自绘或第三方控件需自行提供 UIA provider；缺失 provider 时，客户端只能看到较少的窗口级信息，可能无法取得瓦片级按钮、名称或可执行控件模式。[Microsoft：UI Automation providers](https://learn.microsoft.com/windows/win32/winauto/uiauto-providersoverview) UIA 的 `AutomationId` 只保证同级唯一，而且属性本身不保证存在；控件树会随界面动态生成与变化。[Microsoft：UIA 测试属性与工具](https://learn.microsoft.com/windows/win32/winauto/uiauto-usefortesting) [Microsoft：UIA tree](https://learn.microsoft.com/windows/win32/winauto/uiauto-treeoverview)

因此，对 Seetong 或其他监控客户端，不能先假设所有视频瓦片都可由 UIA 控件名点击。先在目标 Windows 上用 UIA Inspect / Accessibility Insights 记录实际窗口树，分别检查菜单/按钮和视频瓦片是否有稳定 `Name`、`AutomationId`、BoundingRectangle、Invoke/Selection pattern；界面自绘瓦片若未暴露这些信息，再以窗口大小、DPI、布局、相机编号和图像锚点做坐标标定。不要把控件自动化与截图坐标混成一个没有状态检查的点击循环。【现场验证】

## 放大、码流与屏幕巡视盲区

Seetong 官方帮助中心公开了主码流和子码流的不同 RTSP 路径，也给出客户端本地登录和云平台登录的功能差别；这说明相关产品生态可能存在独立的高/低码流，或经授权读取 RTSP 的路径，但不能证明某个具体摄像头、账号或客户端当前使用哪一路。[Seetong：主/子码流 RTSP 配置](https://help.seetong.com/fqa/question/3874/1905458) [Seetong：客户端登录方式](https://help.seetong.com/hot/question/1504659)

截至本次核查，找到的 Seetong 官方帮助页说明了主/子码流路径，但没有说明“单击/双击放大”是否自动从子码流切到主码流，也没有保证切换延迟、帧率或画质。因此不得把点击放大当成已获得主码流或真实高清。用户现场须分别在宫格和单路大画面记录分辨率、帧率/码率（若客户端状态可见）及画面纹理；确认仅布局缩放、解码切流还是服务器端重新请求后，才能决定放大巡视是否有用。【现场验证】Seetong 官方帮助中心还明确指出，已录制画面手动放大会变模糊；这只证明回放数字放大的限制，不能替代对其实时放大实现的判断。[Seetong：回放放大模糊说明](https://help.seetong.com/fqa/question/3874/1529574)

纯屏幕采集只取得采集时刻客户端显示的像素：它看不到客户端之外的码流元数据，不会补出宫格缩小丢失的源细节，也无法同时保留被单路放大挤出屏幕的其他视频路。【推断】若通过已授权 RTSP/SDK 并行读取十路，可改变“屏幕单路串行”的盲区与源像素问题，但这需要账号权限、端口/码流能力、Windows 网络稳定性和负载验收；官方示例地址不是本现场已授权或已验证的接入凭据。【现场验证】

## 建议的学习—执行—恢复流程

1. **一次标定：**锁定监控客户端版本、分辨率、Windows 缩放率、窗口模式和十路名称顺序。优先记录 UIA 语义控件和控件模式；对自绘视频瓦片记录每种布局的相机框中心/边界。计算机使用模型只对困难控件提供候选定位，由操作者确认后写入校准配置。
2. **确定性运行：**状态机只允许已知状态与动作，例如“九宫格 → 相机 4 选中 → 单路视图 → 画面稳定 → 截图/OCR 校验 → 返回原布局”。每步验证实际状态、超时或状态不匹配即停止，不继续盲点。每次运行记录动作、结果、布局、UIA/OCR 读数、时间戳和恢复原因。
3. **有限恢复：**对焦点丢失、弹窗、窗口被遮挡、分辨率/DPI 变化等情况先作有限的一次恢复；状态仍未知时把该轮记为覆盖失败并请求人工，而不是让 VLM 连续试错。客户端更新或布局变化后，使用合成 UI/非生产数据重跑标定和长循环，人工批准配置版本再启用。
4. **分开验收：**分别测控制成功率、切换后首帧就绪时间、每路回访间隔、错误恢复率、十路轮询覆盖率，以及宫格与单路视图的实际可辨别细节。短暂事件是否可见须用独立留出的真实标注样本验证；单纯“十路依次点击成功”不等于十路连续监控，也不证明行为检测召回。

【推断】重复且动作空间窄的 UI 导航适合状态机；在线大模型更适合把自然语言目标转成一次经审阅的校准草案、解释未知弹窗或生成人工复测步骤。每次点击都调用模型会把运行稳定性依赖在模型预测偏差、截图清晰度、显存竞争和推理延迟上。模型 benchmark 是不同测试集上的产品方报告，不能预测当前客户端的点击可靠率、十路覆盖或动作识别准确率。
