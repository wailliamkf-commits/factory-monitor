## 必须修正的计数与状态语义

`runtime.py` 的 `_put_bounded` 在第一次 `put_nowait` 遇到 `Full` 后，尝试取走旧包再重试，即使重试成功仍返回 `False`。若消费者恰好已腾出空间，取旧包得到 `Empty`、重试成功，也可能没有真实丢包但返回 `False`。

因此最后上报的 `81` 是该计数器的累计结果，不是实际丢包数量的严格下限，也不能乘以十解释成每路物理丢帧。录像丢失由独立时间戳与媒体证据确认，不依赖这个计数器。下一版分别记录 `attempted_new`、`accepted_new`、`rejected_new`、`evicted_old`、`consumed`、`remaining`、`shutdown_discarded`，另记首次 Full 及重试成功。静止终态应满足：

- `attempted_new = accepted_new + rejected_new`。
- `accepted_new = consumed + evicted_old + remaining + shutdown_discarded`。

不得用近似 `qsize()` 判断收尾完成或账目正确；用唯一帧序号及明确终态对账。若进程崩溃使最终计数未送达，标记未知，不能据最后一次采样宣称“零丢帧”。

目前 `recording_status=complete` 表示封装过程完成，允许同时存在 `gaps`。GUI 详情已有缺口说明，因此不是完全隐藏缺口，但汇总仍容易误读。后续应保留处理状态，另提供明确的完整性结果（完整/有缺口/未知），在列表、报告、导出中同步显示；未知或有缺口均不能计作完整证据通过。原样视频与时间戳保留，不以补造画面或改变播放帧率伪装完整。

## 根因假设：按优先级验证

下面是代码中可见的机制，不是已经完成的 Windows 性能定位。当前重复计算发生在同一个证据进程中，十路尚未拥有并行的证据写入能力。

1. **目录扫描与清单写入耗时。** 每个活跃事件每收到一帧都调用 `_disk_usage`，递归遍历整个证据根目录；十路同批录制时，每个总画面包触发约十次扫描。每张保留 JPEG 还会重写原子清单。预测：扫描/文件元数据/清单的耗时随已有文件数上升，并占掉大量 500 毫秒输入间隔。
2. **编码、帧写盘或视频封装阻塞消费。** 同一进程串行裁剪、JPEG 编码和写入，末尾再串行封装十段 MP4。预测：这些阶段占主要耗时，或者封装边界使输入等待时长跳升；若前期已经掉帧，末尾封装不能独自解释全部失败。
3. **停止顺序导致队列发送线程不能结束。** 共享 stop 同时停止采集与消费者，而采集可能仍有排队的数据待发送。Python 官方说明生产进程可能等队列后台线程排空后才能退出，符合“stopped 后仍存活”的症状；需 Windows 线程栈证明，不能直接定案。[Python 3.12 队列退出说明](https://docs.python.org/3.12/library/multiprocessing.html#programming-guidelines)
4. **观测器或 Windows 文件环境放大负载。** 已测的日志自耗时很小，但未覆盖所有干扰，也无严格成对实验。只在前述测量不能解释结果时增加对照；不先关闭安全软件、VPN、防火墙或修改系统设置。

### P1：一次有针对性的剖析（Sol）

- 在证据进程中分别计时：取包等待、包等待年龄、裁剪、JPEG 编码、缓存管理、目录扫描及访问文件数、JPEG 写盘、清单序列化/写入/替换、预览、MP4 读取/标注/编码/关闭。用单调时钟，每五秒及阶段转换输出聚合值，区分触发前、触发突发、持续录制、预览、封装；记录探针开销。
- 帧包增加单调序号；记录生产、接受、拒绝、替换旧包、消费和终止状态的独立计数及最终对账。正常消费阶段必须能持续跟上每 500 毫秒一个包；单次突发可有有限积压，但必须收敛，不能靠无限队列遮住问题。
- 保持控制/消息读取可观测，记录停止请求、各 worker 离开循环、目标函数返回、进程真正退出、join 和强制终止的时间。预先装好子进程栈采集机制，在强制终止前记录线程栈；Windows 不使用仅适用于 Unix 的信号假设。
- 默认只重跑一次原十路有探针场景。已有本次原始证据，不再为“确认失败”重复空跑。仅当热点不清晰时追加一次同样十路输入但不触发事件的短对照；仅当观测干扰仍有证据疑点时追加有/无观测器的成对对照。这些对照不能冒充原十路通过。
- P1 完成标准：能给出各阶段耗时排序和随文件数量的变化；队列损失可正确对账；得到 capture 退出阻塞栈或明确指出仍缺哪项证据。没有定位到主耗时/退出位置则保持未定位，不做成串猜测性补丁。

### P2：仅修实测证明的问题（Sol；Terra 执行确定性部分）

- 若目录扫描是主因，采用受约束的增量容量账本，启动/恢复时核对、文件成功写入和删除时更新，计入临时文件、帧、清单、预览和封装峰值；保留磁盘上限、写入失败可见、在途保护。不能简单删掉容量检查。
- 若清单写入占主导，只在保证崩溃恢复和缺口记录可回读的前提下减少冗余重写；不能用更快但丢失恢复证据的方式通过。
- 若封装明显阻塞持续采集，才将封装移入有界任务队列；采集证据继续落盘，完成通知须等待真实封装、读回及错误处理。先证明需要，再引入并发。
- 若退出栈证实队列收尾问题，明确生产结束、检测/候选命令完成、证据及控制消息排空、消费者确认、进程 join 的顺序；结束标记不能越过尚未处理的候选命令。用有界终止机制处理真实失败，保留诊断；不对证据队列随意调用 `cancel_join_thread` 丢弃缓冲，也不吞掉异常。

### P3：集中回归与停止条件（Terra，Root 最终 Gate）

- 为真实问题建立小型定向回归：慢消费/队列 Full 竞争时计数正确；有未发送包时有序停止；缺帧片段不计为完整；容量变化和重启恢复仍正确。故障注入只影响本项目测试进程与临时目录。
- 改进测试结果汇总：即使出现 runtime error，也在 finally/事后检查中继续审计所有十段媒体、时间戳和退出码，一次报告全部失败；保持总判定 FAIL。完整解码，不能只读首帧和容器声明帧数。
- 在同一目标 Windows 用原参数完成两次连续十路回归：十路各一个候选；十段视频和预览全部可回读；每段无缺口、原窗口满足、时长不少于原 88 秒门槛且帧数/时间戳/播放时长相符；队列精确账目无证据拒绝/替换丢失/停止丢弃；所有子进程自然退出 0、无残留、无强制终止。已有文件不覆盖。
